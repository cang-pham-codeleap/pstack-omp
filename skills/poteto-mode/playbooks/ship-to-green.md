### Ship to green

**You coordinate one PR from its first push to the state where the human only merges. You decide, phase agents act, and nothing here merges.** For "ship to green", "open a PR and get it green", "tạo PR rồi lo CI và review đến khi xong". The input is a Jira ticket or a change to build. The loop ends when CI, Copilot, and the repo's approving review are all settled. You are the babysit owner for the run, so the rule in `playbooks/babysit.md` that holds a babysit until a whole stack exists does not apply to you. The loop is GitHub only. On Origin, use `playbooks/babysit.md` in `drive` mode instead. Two or more tickets go to **Many tickets** at the end.

**The coordinator never waits, polls, reads CI logs, or edits code.** You run intake, preflight, one-line GitHub commands, and decisions. Everything else goes to a phase agent that returns a status report. A coordinator that runs `watch-pr`, `gh run watch`, or `sleep` itself pays its whole context on every wake. One audited run did that for 29 turns at about 158k tokens each, about 4.6M input tokens spent waiting on one PR.

| Phase agent | `agent:` | Owns | Returns at |
|---|---|---|---|
| Builder | `poteto-agent`, or `pstack-judgment` for a hard change | the change, gates, evidence, the PR, the first Copilot request | PR open |
| Watcher | `pstack-watch` | `watch-pr`, re-arms on noise, CI log reading and classification, one flake rerun | a verdict that needs a decision |
| Triager | `pstack-code` | each review thread checked against the code | a proposal per thread |
| Fixer | `pstack-code`, or `pstack-judgment` for a sensitive area or a second identical CI failure | the decided fixes, replies, resolutions, re-request | push done and threads verified |

**Every phase agent ends with this status report and nothing else.** Fifteen lines at most. Paste the block into each brief.

```
phase: build | watch | triage | fix
pr: <url>   head: <sha7>   elapsed: <min> (eta <min>)
verdict: <READY | BLOCKER exit N | DONE>
ci: <passed>/<total>; failing: <check> <flake|stale-base|diff> <run url>
copilot: <reviewed sha7 | pending | absent>   approver: <APPROVE | CHANGES | DEFERRED | FAILED <status line> | pending | absent>
thread: <id> <url> <path:line> <fix|dismiss|sensitive> <claim in one line> <resolved yes/no>
evidence: <markdown links already in the PR body>
counts: <watch-pr --status-only "ship" entry: startedAt, copilotReviews, approverRuns, ciFixes>
next: <one line>
```

0. **Intake gate when the input is a Jira ticket.** Fetch the description as markdown and the ticket's comments. Take the hash from the newest comment that reads `Intake complete. type=<type> sha256=<h> ...` and run `node skill://ticket-intake/scripts/check-ticket-ready.mjs --expect=<h>` on the description yourself. Run `skill://ticket-intake` before anything else when there is no such comment, when the result is not `ready: true` (`stale: true` means someone edited the ticket after intake), or when the ticket lacks the `agent-ready` label. Intake grills the human in rounds until every decision and edge case is settled, writes the answers back into the ticket, and stamps it again. Clear acceptance criteria are not an exemption. One audited run built CP-3753 without intake because its criteria "were unambiguous", while the checker reported `ready: false` with a blank Instance and no intake type. This is the only step that asks the human anything. A ready ticket starts at once. Input that is not a ticket skips this step.
1. **Preflight before any push.**
   - Run `gh auth status`. When more than one account is logged in, confirm the active one owns the branch and has `repo` scope (`gh api user --jq .login`). Stop and report on a mismatch.
   - Never run `gh auth token`, and never read, create, or set a secret or token for any reason. A CI failure that seems to need a credential is a stop condition.
   - Find the repo's approving review trigger. Search `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, and `.github/workflows/*` for an `issue_comment` workflow that answers a comment command such as `/review`. Record the exact command, the workflow's `name:`, and the login of the bot that posts the review. Call it the **approver**. Every later step uses the recorded command, never a guessed `/review`. No match means no approver, and step 5 is skipped with a note.
   - Run `skill://poteto-mode/scripts/watch-pr/watch-pr eta --approver-workflow "<approver workflow name>"`. It reads the repo's GitHub Actions history and prints p50 and p90 seconds per workflow plus a `recommended` block: `copilotReviewTimeout`, `approverReviewTimeout`, `ciTimeout`, and `runBudget`. Copilot's runs are matched by name (`Copilot`, `Copilot code review`, `Running Copilot Code Review`). Use those numbers as they are. `runBudget` is the run's time cap, counted from the PR's `createdAt`.
   - Find the evidence surface: the Storybook, preview URL, or local dev server where the change is visible.
2. **Build, prove, and open the PR with the Builder.** The Builder works in its own worktree. It builds the change with Feature or Bug fix, using the ticket's delivery block for branch, gates, and acceptance commands. The Builder never asks the human. Where Feature or Bug fix would ask, it decides within the ticket's **Agent discretion** and records the call in the PR description, or it reports a blocker. Every user-visible change ships evidence from the real surface. A static state gets before and after screenshots. Hover, click order, focus, motion, or any multi-step flow gets a recording per `skill://video-evidence`. A change with nothing visible gets the command output that proves it. It captures the files in the same `browser` tab it verifies with (`tab.screenshot`, `tab.recordStart`), before and after the change, so evidence costs no extra session. Each file needs its own name (`before-card.png`, `after-card.png`); the script rejects two files with the same name. It opens the PR through `playbooks/opening-a-pr.md`, ready and never draft. Then, in the PR's worktree with the PR head checked out and pushed, it runs `skill://poteto-mode/scripts/pr-evidence <files…>`. The script commits the files under `.pr-evidence/` on branch `evidence/<working branch>`, pushes it, and prints a `Captured against <sha>` line followed by SHA-pinned markdown. The evidence branch holds no code and shares no history with the PR, so it starts no CI and no preview deploys. The PR branch never carries the files. The Builder puts those lines in the PR body under `## Evidence` with `gh pr edit <n> --body-file <file>`. Then it runs `gh pr edit <n> --add-reviewer @copilot`. When the Copilot request fails, it adds one line to the PR description saying no Copilot review was available. It reports the head SHA it pushed. Before arming the Watcher, read the diff and run `curl -sfI` on each `## Evidence` link. A PR with a visible change and no working evidence goes back to the Builder.
   GitHub plays no video committed to a branch; it shows only "View raw". So for each `.mp4`, `.webm`, `.mov`, or `.mkv` the script also commits a GIF (10 fps, at most 960 px wide, needs `ffmpeg`) and prints it inline with the original linked below it. Keep each recording short, under about 15 seconds, so the GIF stays small enough to load in the PR.
   Evidence is readable by anyone who can read the repo, and SHA-pinned blobs stay reachable after the PR closes. Never capture secrets, tokens, or real customer data. After the PR merges, delete the branch with `git push origin --delete evidence/<working branch>`.
3. **Arm the Watcher.** Brief it with the PR, the head SHA the Builder or Fixer pushed, the timeouts from step 1, and the reviewer to await. It runs `watch-pr --pr <n> --head <sha> --timeout <s> [--await-review copilot --review-timeout <copilotReviewTimeout>]` in the foreground of its own context. `--timeout` is always the run budget still left: `runBudget` minus the seconds since `startedAt`. Pass `--await-review copilot` only when a Copilot request is outstanding for that head; after the Copilot cap, or when the request failed, leave it out. The watcher prints NDJSON and the terminal verdict is the last line, so it never pipes the output through `head` or `cut`. Every verdict carries the head SHA it describes. It handles noise itself and returns only for a decision. Exit 5 or 7 gets one re-arm with the budget left. Exit 8 means the head moved: when the push was ours, re-arm with the new SHA; otherwise it is a stop per step 7. A failing check gets its log read and a class. A flake or infrastructure failure gets one `gh run rerun <run-id>`, never `--failed`, then a re-arm. A failure in code the diff never touched is checked with `git merge-base --is-ancestor` and reported as `stale-base`. Exactly one Watcher runs per PR. Re-arm after every push wave.
4. **Decide on the report.** Order is conflicts, then threads, then CI.
   - **Conflict (exit 2).** Stop and report which branch needs the rebase. Do not resolve it.
   - **Threads (exit 3).** Spawn the Triager. It reads every unresolved thread, checks the claim against the code, and proposes `fix` or `dismiss` per `references/code-review-bot-triage.md` with one change. The `ask` class does not exist here. A thread in a sensitive area (security, privacy, auth, billing, data, migration, concurrency) is **fix or stop**. You make each call. A `stop` labels the PR `agent-blocked`, comments the exact gap, and ends the run. Then spawn the Fixer with the decided list. It makes one new commit for the fixes, pushes, and replies and resolves each thread with `watch-pr resolve-thread --pr <n> --thread <id> --body-file <reply-file>`. The reply names the commit SHA, or the reason for a dismissal. Reply text goes in a file as data, never interpolated into a command. A thread that repeats a comment already resolved on the same path gets the earlier reason quoted, is resolved again, and is not a new finding. The Fixer then reads every thread's `isResolved` back from GitHub and reports any that is still open. It re-captures evidence when a fix changes what the evidence shows.
   - **Failing check in the diff (exit 4, class `diff`).** Spawn the Fixer for one fix commit. Read the count from `watch-pr --pr <n> --status-only`: `ship.ciFixes.<check>` counts the pushes that followed a failure of that check. At the third fix for one check, label `agent-blocked`, comment, and stop. Never edit a test to weaken it, skip or disable a check, pass `--no-verify`, or touch required-check settings.
   - **Stale base (exit 4, class `stale-base`).** Run `gh pr update-branch <n>` once. It merges the base into the branch without a force push. Re-arm with the new head. A second stale-base, or an update-branch that reports a conflict, is a stop and a report.
   - **Copilot review timeout (exit 9 on `copilot`).** Add one line to the PR description, then re-arm without `--await-review copilot`.
   - **Changes requested (exit 6).** The verdict's `blocker.reviews` names each awaited reviewer and its matched review. A `CHANGES_REQUESTED` from an awaited reviewer on an older head does not end the watch. The Watcher reports `AWAITING_REVIEW` until that reviewer reviews the new head. So after fixing an approver's requested changes, re-trigger the approver per step 5 and arm with `--await-review <approver-login>`. Exit 6 then means a request on the current head, or one from a reviewer you are not awaiting. The approver's own findings go through step 5. A request from a human, or a closed PR, is a stop and a report.
   - **After each fix push.** When `ship.copilotReviews` from `watch-pr --status-only` is below 2, the Fixer requests Copilot again. Copilot does not re-review a push on its own. At 2 reviews, do not request again, and arm without `--await-review copilot`.
5. **Settle the approver last.** Only when the Watcher reports `READY` with Copilot satisfied or noted absent, note the time as an ISO timestamp, post the recorded approver command with `gh pr comment <n> --body "<command>"`, and arm the Watcher with `--head <sha> --await-review <approver-login> --since <time> --review-timeout <approverReviewTimeout> --timeout <budget left>`. Only an `APPROVED` or `CHANGES_REQUESTED` review of that head, submitted after `--since`, settles the wait. The `AWAITING_REVIEW` and `READY` lines carry the matched review's state, time, and body excerpt, so the Watcher reports them as they are. Every approver finding gets an outcome on the PR, LOW ones included. Fix it through step 4, or reply on the PR with why it is out of scope. A finding that lives only in your chat reply is not settled. A review that requests changes goes back through step 4, then triggers the approver once more. A `VERDICT: DEFERRED` review (state `COMMENTED`) means CI was still pending, so wait for `READY` and trigger again. A deferral does not count toward the 2-run cap, because `ship.approverRuns` subtracts it. Exit 10 means the approver run failed without a review. The verdict's `failure.excerpt` carries the status line of the workflow's `pr-review-status` comment. Read that line and the workflow run. An unauthorized requester, a PR that GitHub Actions opened, or a run that never started is a stop and a report, because a retry fails the same way. Any other failure gets one more trigger within the cap, armed with a new `--since`. Exit 9 on the approver means it stayed silent: no review and no failure comment came in time. Read its workflow run for the trigger comment. A run that never started, or a review login that never matches, is a stop and a report. A run that is still queued gets one re-arm with the same `--since`. The approver runs at most 2 times, counted by `ship.approverRuns` from `watch-pr --pr <n> --status-only --approver-command "<command>"`.
6. **Stop on the first of these.** Done means `READY`, Copilot satisfied or noted absent, every thread resolved on GitHub, and the approver satisfied or absent. Before you call it done, run `watch-pr --pr <n> --head <sha> --status-only --await-review <each awaited login> --approver-command "<command>"` once yourself, and `curl -sfI` each evidence link in the PR body. A missing review, an open thread, or a link that does not answer means not done. The caps are 2 Copilot reviews, 2 approver runs, 3 CI fixes per check, and `runBudget` from `eta` counted from the PR's `createdAt`. All of them come from the `ship` entry of `watch-pr --status-only`, read at every report. On a cap or a blocker, post one comment on the PR with the exact gap and the commands tried, add the `agent-blocked` label when the repo has it, and stop. Never run `gh pr merge`, never arm auto-merge, and never mark a PR approved yourself.
7. **Fixes are new commits.** Never amend and never force-push, so review threads keep their anchor. A push from someone else while the loop runs, or a conflict you did not create, is a stop and a report.
8. **Record what the run taught.** At the end, stop or done, the coordinator writes lessons per `skill://lessons`. Phase agents never write. Each one lists candidate lessons in its report. A human change request or an approver finding that the ticket should have specified is an `intake-gap` for that ticket's type and section. A CI or review fix whose cause the Fixer verified is a `root-cause` with the files it touched. Vote on every lesson that intake or the Builder matched and used.

Do not swarm-verify. This playbook buys speed and low cost over a second audit.

#### Many tickets

For two or more tickets at once. The root coordinates owners and never runs phase agents for them.

1. **Intake every ticket first.** Run the checker on all of them with `--expect=<h>` from each ticket's newest `Intake complete ... sha256=<h>` comment, as in step 0. A missing stamp or a mismatch means that ticket needs intake again. Run `skill://ticket-intake` for each one that is not ready, and put each round's frontier for all tickets into one `ask`, with every question tagged by its ticket key. After this step no owner asks the human anything.
2. **Separate the work.** Map which files each ticket will touch from its scope. Tickets that touch the same component go to one owner in sequence. Every other ticket gets its own owner, worktree, and branch off the base.
3. **One owner per ticket.** Spawn a `poteto-agent` per ticket that runs steps 1 to 7 as the coordinator of its own PR. Keep at most 4 owners live, since each owner keeps one phase agent running and `task.maxConcurrency` defaults to 8. Queue the rest, and start the next owner when one finishes.
4. **Keep a ledger, not a context.** Each owner returns the status report at the end and on a stop. Keep one row per ticket with the PR, head, verdict, Copilot rounds, approver result, elapsed, and blocker. After a restart, rebuild every row from GitHub: `gh pr list --author @me --state open --json number,headRefName` finds the PRs, and `watch-pr --pr <n> --status-only --approver-command "<command>"` gives each one's counts and `startedAt`. Owners re-run `watch-pr eta` before each arm, because ten PRs at once queue on the same CI runners and the Copilot reviewer.
5. **End merge-ready.** Every PR stops at step 6. Landing them is `playbooks/shipping.md` or `playbooks/autopilot-full.md`.

**Reply:** the PR link. The intake checker result and whether intake ran. The final state of CI, Copilot, and the approver. Each thread with its URL, fixed or dismissed with the reason, and its resolved state read from GitHub. Each approver finding and where on the PR it was answered. The evidence links in the PR body. The counts against the caps, and elapsed time against the `eta` estimate. Each principle that changed a decision, and the decision. Anything that stopped the loop and needs the human. For many tickets, the ledger as a table.
