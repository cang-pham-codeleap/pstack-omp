### Ship to green

**You coordinate one PR from its first push to the state where the human only merges. You decide, phase agents act, and nothing here merges.** For "ship to green", "open a PR and get it green", "tạo PR rồi lo CI và review đến khi xong". The input is a Jira ticket or a change to build. The loop ends when CI, Copilot, and the repo's approving review are all settled. You are the babysit owner for the run, so the rule in `playbooks/babysit.md` that holds a babysit until a whole stack exists does not apply to you. The loop is GitHub only. On Origin, use `playbooks/babysit.md` in `drive` mode instead. Two or more tickets go to **Many tickets** at the end.

**The coordinator never waits, polls, reads CI logs, or edits code.** You run intake, preflight, one-line GitHub commands, and decisions. Everything else goes to a phase agent that returns a status report. A coordinator that runs `watch-pr`, `gh run watch`, or `sleep` itself pays its whole context on every wake. One audited run did that for 29 turns at about 158k tokens each, about 4.6M input tokens spent waiting on one PR.

| Phase agent | `agent:` | Owns | Returns at |
|---|---|---|---|
| Builder | `poteto-agent`, or `pstack-judgment` for a hard change | the change, gates, evidence, the PR, the first Copilot request | PR open |
| Watcher | `pstack-watch` | `watch-pr`, re-arms on noise, CI log reading and classification, one flake rerun | a verdict that needs a decision |
| Triager | `pstack-code` | each review thread checked against the code | a proposal per thread |
| Fixer | `pstack-code`, or `pstack-judgment` for a sensitive area or a second identical CI failure | the decided fixes, replies, resolutions, re-request | push done and threads verified |

**Every phase agent ends with this status report and nothing else.** Fifteen lines at most. Paste the block into each brief.

```
phase: build | watch | triage | fix
pr: <url>   head: <sha7>   elapsed: <min> (eta <min>)
verdict: <READY | BLOCKER exit N | DONE>
ci: <passed>/<total>; failing: <check> <flake|stale-base|diff> <run url>
copilot: <reviewed sha7 | pending | absent>   approver: <APPROVE | CHANGES | DEFERRED | pending | absent>
thread: <id> <url> <path:line> <fix|dismiss|sensitive> <claim in one line> <resolved yes/no>
evidence: <markdown links already in the PR body>
ship-state: <watch-pr ship-state JSON>
next: <one line>
```

0. **Intake gate when the input is a Jira ticket.** Fetch the description as markdown and run `node skill://ticket-intake/scripts/check-ticket-ready.mjs` on it yourself. When the result is not `ready: true` or the ticket lacks the `agent-ready` label, run `skill://ticket-intake` before anything else. It brainstorms the target with the human, writes the answers back into the ticket, and stamps it. Clear acceptance criteria are not an exemption. One audited run built CP-3753 without intake because its criteria "were unambiguous", while the checker reported `ready: false` with a blank Instance and no intake type. This is the only step that asks the human anything. A ready ticket starts at once. Input that is not a ticket skips this step.
1. **Preflight before any push.**
   - Run `gh auth status`. When more than one account is logged in, confirm the active one owns the branch and has `repo` scope (`gh api user --jq .login`). Stop and report on a mismatch.
   - Never run `gh auth token`, and never read, create, or set a secret or token for any reason. A CI failure that seems to need a credential is a stop condition.
   - Find the repo's approving review trigger. Search `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, and `.github/workflows/*` for an `issue_comment` workflow that answers a slash command such as `/review`. Record the command and the login of the bot that posts the review. Call it the **approver**. No match means no approver, and step 5 is skipped with a note.
   - Run `skill://poteto-mode/scripts/watch-pr/watch-pr eta`. It reads the repo's GitHub Actions history and prints p50 and p90 seconds per workflow, Copilot's review runs included under the workflow name `Copilot`. Set Copilot's `--review-timeout` to twice its p90, the approver's to twice its p90, and the expected CI wait to the p90 of the PR workflow. Fall back to 600, 900, and 900 seconds when a workflow has fewer than 3 samples.
   - Find the evidence surface: the Storybook, preview URL, or local dev server where the change is visible.
2. **Build, prove, and open the PR with the Builder.** The Builder works in its own worktree. It builds the change with Feature or Bug fix, using the ticket's delivery block for branch, gates, and acceptance commands. Every user-visible change ships evidence from the real surface. A static state gets before and after screenshots. Hover, click order, focus, motion, or any multi-step flow gets a recording per `skill://video-evidence`. A change with nothing visible gets the command output that proves it. It captures the files in the same `browser` tab it verifies with (`tab.screenshot`, `tab.recordStart`), before and after the change, so evidence costs no extra session. It opens the PR through `playbooks/opening-a-pr.md`, ready and never draft. Then, in the PR's worktree, it runs `skill://poteto-mode/scripts/pr-evidence <files…>`. The script commits the files under `.pr-evidence/` on branch `evidence/<working branch>`, on top of the working branch's HEAD, pushes it, and prints SHA-pinned markdown. The PR branch never carries the files. The Builder puts those lines in the PR body under `## Evidence` with `gh pr edit <n> --body-file <file>`. It runs `watch-pr ship-state --pr <n>`, then `gh pr edit <n> --add-reviewer @copilot` and `watch-pr ship-state --pr <n> --inc review`. When the Copilot request fails, it adds one line to the PR description saying no Copilot review was available. Before arming the Watcher, read the diff and confirm the `## Evidence` links resolve (`gh pr view <n> --json body`). A PR with a visible change and no evidence goes back to the Builder.
3. **Arm the Watcher.** Brief it with the PR, the timeouts from step 1, and the awaited reviewer. It runs `watch-pr --pr <n> --await-review copilot --review-timeout <s>` in the foreground of its own context. The watcher prints NDJSON and the terminal verdict is the last line, so it never pipes the output through `head` or `cut`. It handles noise itself and returns only for a decision. Exit 5 or 7 gets one re-arm. A failing check gets its log read and a class. A flake or infrastructure failure gets one `gh run rerun <run-id>`, never `--failed`, then a re-arm. A failure in code the diff never touched is checked with `git merge-base --is-ancestor` and reported as `stale-base`. Exactly one Watcher runs per PR. Re-arm after every push wave.
4. **Decide on the report.** Order is conflicts, then threads, then CI.
   - **Conflict (exit 2).** Stop and report which branch needs the rebase. Do not resolve it.
   - **Threads (exit 3).** Spawn the Triager. It reads every unresolved thread, checks the claim against the code, and proposes `fix` or `dismiss` per `references/code-review-bot-triage.md` with one change. The `ask` class does not exist here. A thread in a sensitive area (security, privacy, auth, billing, data, migration, concurrency) is **fix or stop**. You make each call. A `stop` labels the PR `agent-blocked`, comments the exact gap, and ends the run. Then spawn the Fixer with the decided list. It makes one new commit for the fixes, pushes, and replies and resolves each thread with `watch-pr resolve-thread --pr <n> --thread <id> --body-file <reply-file>`. The reply names the commit SHA, or the reason for a dismissal. Reply text goes in a file as data, never interpolated into a command. A thread that repeats a comment already resolved on the same path gets the earlier reason quoted, is resolved again, and is not a new finding. The Fixer then reads every thread's `isResolved` back from GitHub and reports any that is still open. It re-captures evidence when a fix changes what the evidence shows.
   - **Failing check in the diff (exit 4, class `diff`).** Spawn the Fixer for one fix commit. Count it with `watch-pr ship-state --pr <n> --inc ci:<check>`. At the third fix for one check, label `agent-blocked`, comment, and stop. Never edit a test to weaken it, skip or disable a check, pass `--no-verify`, or touch required-check settings. A `stale-base` class is a stop and a report.
   - **Review timeout (exit 9).** Add one line to the PR description, then re-arm without `--await-review copilot`.
   - **Changes requested by a human, or a closed PR (exit 6).** Stop and report.
   - **After each fix push.** When `reviewRounds` is below 2, the Fixer requests Copilot again and runs `ship-state --inc review`. Copilot does not re-review a push on its own. At 2 rounds, do not request again.
5. **Settle the approver last.** Only when the Watcher reports `READY` with Copilot satisfied or noted absent, post the approver's slash command with `gh pr comment <n> --body "/review"` and arm the Watcher with `--await-review <approver-login> --review-timeout <s>`. Every approver finding gets an outcome on the PR, LOW ones included. Fix it through step 4, or reply on the PR with why it is out of scope. A finding that lives only in your chat reply is not settled. A review that requests changes goes back through step 4, then triggers the approver once more. A `VERDICT: DEFERRED` comment means CI was still pending, so wait for `READY` and trigger again. The approver runs at most 2 times. An approver that rejects the requester as unauthorized is a stop.
6. **Stop on the first of these.** Done means `READY`, Copilot satisfied or noted absent, every thread resolved on GitHub, and the approver satisfied or absent. The caps are 2 Copilot reviews, 2 approver runs, 3 CI fixes per check, and 60 minutes from the recorded start, checked at every report. On a cap or a blocker, post one comment on the PR with the exact gap and the commands tried, add the `agent-blocked` label when the repo has it, and stop. Never run `gh pr merge`, never arm auto-merge, and never mark a PR approved yourself.
7. **Fixes are new commits.** Never amend and never force-push, so review threads keep their anchor. A push from someone else while the loop runs, or a conflict you did not create, is a stop and a report.

Do not swarm-verify. This playbook buys speed and low cost over a second audit.

#### Many tickets

For two or more tickets at once. The root coordinates owners and never runs phase agents for them.

1. **Intake every ticket first.** Run the checker on all of them. Run `skill://ticket-intake` for each one that is not ready, and batch the questions for all tickets into as few `ask` rounds as possible. After this step no owner asks the human anything.
2. **Separate the work.** Map which files each ticket will touch from its scope. Tickets that touch the same component go to one owner in sequence. Every other ticket gets its own owner, worktree, and branch off the base.
3. **One owner per ticket.** Spawn a `poteto-agent` per ticket that runs steps 1 to 7 as the coordinator of its own PR. Keep at most 4 owners live, since each owner keeps one phase agent running and `task.maxConcurrency` defaults to 8. Queue the rest, and start the next owner when one finishes.
4. **Keep a ledger, not a context.** Each owner returns the status report at the end and on a stop. Keep one row per ticket with the PR, head, verdict, Copilot rounds, approver result, elapsed, and blocker. Rebuild it from `watch-pr ship-state` after a restart. Owners re-run `watch-pr eta` before each arm, because ten PRs at once queue on the same CI runners and the Copilot reviewer.
5. **End merge-ready.** Every PR stops at step 6. Landing them is `playbooks/shipping.md` or `playbooks/autopilot-full.md`.

**Reply:** the PR link. The intake checker result and whether intake ran. The final state of CI, Copilot, and the approver. Each thread with its URL, fixed or dismissed with the reason, and its resolved state read from GitHub. Each approver finding and where on the PR it was answered. The evidence links in the PR body. The counts against the caps, and elapsed time against the `eta` estimate. Each principle that changed a decision, and the decision. Anything that stopped the loop and needs the human. For many tickets, the ledger as a table.
